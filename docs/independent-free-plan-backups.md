# The Milano Seal — Independent Supabase Free-plan Backup Runbook

## Current status (2026-11-10)
Backup automation is **prepared, not operational**, until the GitHub repository secrets and independent S3-compatible bucket are configured and the first successful restore drill is performed. Do not represent a successful upload as a successful restoration.

Production Supabase project: `ehqdzfopsrbwewtddiwq` (`supabase-teal-chair`). Database: PostgreSQL 17.
Three private buckets: `documents`, `evidence`, `deal-documents`.

## What is captured
- `roles.sql`, `schema.sql`, `data.sql` generated by the Supabase CLI.
- Separate custom-format data-only export of `auth` and `storage` metadata (not captured in the default CLI schema/data dump).
- Actual Storage object bytes from the three private buckets with per-object SHA-256.
- Expected Storage object counts read directly from the database; the backup fails if object counts do not match.
- Everything is locally encrypted with GPG AES-256 before uploading to an **independently owned S3-compatible storage bucket**. GitHub Actions stores no plaintext backup artifact.

Important caveats: Supabase CLI excludes managed schemas; the separate managed-data export is **supplemental** and is not a validated drop-in restoration into an existing hosted Supabase project. OAuth configuration, JWT and API secrets, SMTP, external integrations, Edge Functions, third-party service data, and encryption root keys are **not** automatically backed up by this workflow. Keep these separately documented in a secure offline vault. Never write production secrets to GitHub commits or logs.

## Operator setup (must be performed before this is enabled)
1. Create an independently owned, **private** S3-compatible bucket (Cloudflare R2 or Backblaze B2); disable public access. Enable versioning/retention where supported, restrict deletion permissions, and require MFA on the storage account. The bucket must not be in Supabase.
2. Create scoped S3 credentials with permission to upload backup objects and check their existence, not to delete all backups. Configure immutable/object-lock retention if supported. Recommend daily backups kept for at least 30 days and monthly archives for 12 months; set lifecycle policies on the bucket separately.
3. In GitHub repository **Settings → Secrets and variables → Actions**, set:
   - `BACKUP_SUPABASE_DB_URL`: database **direct connection or session pooler port 5432**, with TLS enforced and backup-capable database credentials. Do not use transaction pooler port 6543.
   - `BACKUP_SUPABASE_SERVICE_ROLE_KEY`: server-only key for this exact project, used for reading private Storage objects.
   - `BACKUP_GPG_PASSPHRASE`: long unique high-entropy encryption phrase; retain a protected **offline copy** independently of GitHub.
   - `BACKUP_S3_ENDPOINT`: full HTTPS S3 endpoint.
   - `BACKUP_S3_BUCKET`: private destination bucket name.
   - `BACKUP_S3_ACCESS_KEY_ID`, `BACKUP_S3_SECRET_ACCESS_KEY`: scoped independent storage credentials.
4. Verify that Actions are enabled; merge the reviewed pull request into main only after the secrets and bucket exist. A failed schedule run must alert the operator (enable GitHub Actions failure notifications).
5. Start **Actions → Independent encrypted Supabase backup → Run workflow**. Confirm all steps succeed; verify the external bucket contains an encrypted `backup.tar.gpg` and `backup.sha256` under the same timestamp. The workflow checks remote object existence and size; manually verify download/hash.
6. The backup cron is `07:17 UTC` each day (GitHub scheduled workflows may be delayed; not a guaranteed execution time). Do not treat the schedule alone as evidence a backup happened. Implement an independent monitor of the most recent remote object age and notify if older than 26 hours.

## Safe restore drill (off production)
1. Download `backup.tar.gpg` and `backup.sha256` to a secured workstation. Compare `sha256sum backup.tar.gpg` with the SHA-256 recorded in the downloaded hash file.
2. Decrypt locally with `gpg --decrypt --output backup.tar backup.tar.gpg`. Only proceed if decryption exits successfully. Store and handle unencrypted material on an encrypted, access-controlled disk, then securely dispose of it according to policy.
3. Extract to an **isolated temporary directory** (do not blindly extract untrusted archives, and never target production).
4. Check all `storage/manifest.json` entries against actual file SHA-256 values, sizes, and counts; verify no missing objects.
5. Create a **separate disposable test Supabase project or isolated self-hosted environment** with compatible PostgreSQL, auth, extensions, and Storage versions. Consult the latest official Supabase migration/restore documentation before replaying `roles.sql`, `schema.sql`, `data.sql`. Do not blindly import the supplemental `auth-storage-data.dump` into a hosted project: managed schemas and encryption-key compatibility require project-specific review.
6. Restore Storage binary objects in the test destination through authenticated Storage APIs and reconcile with metadata. Recreate required app integrations, Auth provider settings, secrets, and project-specific keys from the operator's vault. Test login, authorization/RLS, client document access, retrieval, audit history, and critical transactions on test accounts only.
7. Record restore date, elapsed time, recovery point, table/object counts, errors, and signed operator approval. Until tested successfully, **recovery is not certified**.

## Failure handling
Any database export error, bucket mismatch, download failure, encryption failure, upload failure, or object verification error fails the GitHub run. Do not delete working source data, disable RLS, expose backup blobs publicly, or push sensitive exports to GitHub Actions artifacts.

## Limitations
This is a daily logical snapshot, not continuous point-in-time recovery. Up to a full day of changes could be lost even if the schedule runs perfectly. GitHub's runner duration and free quota may limit large backups. The workflow depends on reachable Supabase and independent S3 services; periodically test from fresh machines.
