## What is captured
- `roles.sql`, `schema.sql`, `data.sql` generated by the Supabase CLI.
- Separate custom-format data-only export of `auth` and `storage` metadata (not captured in the default CLI schema/data dump).
- Actual Storage object bytes from the three private buckets with per-object SHA-256.
- Expected Storage object counts read directly from the database; the backup fails if object counts do not match.
- Everything is locally encrypted with GPG AES-256 before uploading to an **independently owned S3-compatible storage bucket**. GitHub Actions stores no plaintext backup artifact.

Important caveats: Supabase CLI excludes managed schemas; the separate managed-data export is **supplemental** and is not a validated drop-in restoration into an existing hosted Supabase project. OAuth configuration, JWT and API secrets, SMTP, external integrations, Edge Functions, third-party service data, and encryption root keys are **not** automatically backed up by this workflow. Keep these separately documented in a secure offline vault. Never write production secrets to GitHub commits or logs.

## Safe restore drill (off production)
1. Download `backup.tar.gpg` and `backup.sha256` to a secured workstation. Compare `sha256sum backup.tar.gpg` with the SHA-256 recorded in the downloaded hash file.
2. Decrypt locally with `gpg --decrypt --output backup.tar backup.tar.gpg`. Only proceed if decryption exits successfully. Store and handle unencrypted material on an encrypted, access-controlled disk, then securely dispose of it according to policy.
3. Extract to an **isolated temporary directory** (do not blindly extract untrusted archives, and never target production).
4. Check all `storage/manifest.json` entries against actual file SHA-256 values, sizes, and counts; verify no missing objects.
5. Create a **separate disposable test Supabase project or isolated self-hosted environment** with compatible PostgreSQL, auth, extensions, and Storage versions. Consult the latest official Supabase migration/restore documentation before replaying `roles.sql`, `schema.sql`, `data.sql`. Do not blindly import the supplemental `auth-storage-data.dump` into a hosted project: managed schemas and encryption-key compatibility require project-specific review.

## Revision and archive integrity checks

- `python3 scripts/backups/test_backups.py -v` runs offline without provider access. PR CI and the existing backup workflow both run it.
- Storage enumeration advances by actual rows returned and stops only on an empty page. Nested object keys and duplicate basenames are preserved; duplicate pages and malformed paths fail closed.
- Before downloading, capture all three bucket inventories with object IDs, update timestamps, and available ETag/size metadata. After all downloads, compare every bucket again. Same-name overwrites and earlier-bucket changes invalidate the export.
- The manifest records each downloaded object revision, byte count and SHA-256. It is written only after all revision comparisons pass. Missing revisions or partial downloads do not produce a success manifest.
- Offline verification rejects object, directory and database-export symlinks before resolving their targets.
- These checks detect observed revision changes; they do **not** establish a shared database-and-Storage point-in-time snapshot. Separate dump commands are also not one database snapshot. A controlled write-free window or another proven consistency mechanism is still needed for recovery certification; do not silently disable production writes.

## Failure handling
Any database export error, bucket mismatch, download failure, encryption failure, upload failure, or object verification error fails the GitHub run. Do not delete working source data, disable RLS, expose backup blobs publicly, or push sensitive exports to GitHub Actions artifacts.

## Limitations
This is a scheduled best-effort logical export, not a shared database/Storage snapshot or continuous point-in-time recovery. No RPO/RTO or recoverable point has been measured; separate dump commands and object revisions alone cannot establish one. GitHub's runner duration and free quota may limit large backups. The workflow depends on reachable Supabase and independent S3 services; periodically test from fresh machines.
