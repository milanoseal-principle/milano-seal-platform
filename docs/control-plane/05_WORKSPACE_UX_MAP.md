# The Milano Seal™ — Workspace & UX Map

## Presentation Principle

Present Milano Seal by user workspace, not by implementation module. The user should experience one international document-execution Matter, not separate RON, apostille, courier, Trust, authority, reconciliation or intelligence products.

## Public Workspace

Purpose: international document authority, education, professional acquisition, referrals and secure entry into Matter intake.

May show:
- Public services and destination/document authority pages.
- Hague Apostille Convention education with current verified status language.
- RON / mobile / in-person execution options with clear conditional boundaries.
- Apostille, authentication and legalization explanations.
- Professional and institutional entry points.
- Intake and approved public pricing/positioning.
- Public trust/compliance explanations supported by verified sources.

Must not show:
- Private Matter data.
- Internal operator intelligence.
- Alliance-private data.
- Destination-only legal conclusions.
- Automatic RON suitability claims.
- Automatic apostille conclusions.
- Unverified claims or fabricated telemetry.

## Client Workspace — `/portal`

Purpose: one client sees only that client's governed international Matter experience.

Primary presentation:
- Matter status.
- Required client actions and missing document facts.
- Documents and upload state.
- Invoice/payment state.
- Schedule status.
- RON / execution status when applicable.
- Apostille/authentication/legalization progress.
- Custody/release status appropriate for the client.
- International delivery tracking.
- Messages/notifications appropriate for the client.
- Completed Matter history.
- Start another Matter.

The client does not need separate Trust Engine, Reconciliation Center, Compliance Atlas, Authority Intelligence or Courier products. Those systems support the Matter experience behind the scenes.

## Operator Workspace — `/dashboard`

Primary information architecture:

- **Today** — what requires attention now.
- **Matters** — canonical Matter records and international execution facts.
- **Execution** — intake, RON/notarial review, dispatch, apostille/authentication/legalization, packaging, custody, courier, delivery and release.
- **Intelligence** — exceptions, reconciliation, country/authority provenance, trust and relationship context.
- **Finance** — Wise settlement, revenue, discounts and governed reporting.
- **Network** — Alliance, RON/notarial, courier, translation and partner operations.
- **Growth** — acquisition, country/document authority, referrals, return clients and verticals.
- **System** — Control Plane, settings, SOP, deployment/readiness and administration.

Operator decision model:
1. What document is this and where was it issued?
2. Where is it going and who will receive it?
3. Is notarization required? If yes, what notarial act and execution method are actually supported?
4. Is the operative path state apostille, federal authentication, non-Hague/legalization or review-required?
5. What is canonically true about payment, execution, authority, custody and delivery?
6. What blocks progression and what is the governed next action?

## VA Workspace — `/va/dashboard`

Purpose: assigned operational support only.

Allowed:
- Assigned tasks.
- Missing-input follow-up.
- Evidence/document collection.
- Approved procedural steps.
- Scoped status updates where policy allows.

Not allowed:
- Finance authority.
- Payment settlement authority.
- RON/notarial-act approval.
- Country/authority route approval.
- Release authority.
- Hidden founder intelligence.
- Uncontrolled Matter state mutation.

## Alliance Workspace — `/alliance/dashboard`

Purpose: scoped partner execution.

Primary presentation:
- Profile and certification/compliance.
- Availability/capacity.
- Assigned work.
- RON/mobile/in-person execution instructions where applicable.
- Witness/document handling instructions.
- Proof submission.
- Assignment status.
- Partner-appropriate payment/benefit information when governed.

Alliance Intelligence remains primarily an operator/system interpretation layer. It must not expose unrelated partner data or create synthetic rankings.

## System Control Plane — `/dashboard/control-plane`

Purpose: explain and govern the platform itself.

It must make visible:
- five-system hierarchy
- canonical Matter and authority model
- 129-party HCCH Apostille Convention coverage metadata
- RON / notarial / state / federal / non-Hague execution lanes
- receiving-authority boundary
- module and route ownership
- readiness states
- duplicate prevention
- placement gate
- production SHA and validation posture

## Mobile Rule

All five primary presentation layers and the operator Control Plane must remain usable on mobile. Shared Milano chrome, navigation, safe-area behavior, responsive tables/cards, reduced-motion handling and role boundaries remain production-gated.
